# auth-claims-stamp-revocation — Scenarios

Each scenario is keyed by its `REQ-*` requirement ID. Implementations are tested in `tests/CoppAddresd.UnitTests` and `tests/CoppAddresd.IntegrationTests`. Format: Given/When/Then.

---

## REQ-CLAIMS-01 — Permission code claims at login

### Scenario: Login emits every permission code

- GIVEN a user with direct permission `Users.View` AND role `Admin` granting `Roles.Assign`
- WHEN the user logs in successfully via `AuthService.LoginAsync`
- THEN the issued access token contains claims for both `Users.View` and `Roles.Assign`
- AND claim values equal the canonical `PermissionCodes.*` string constants

### Scenario: Login with no permissions

- GIVEN a user with no direct permissions and no roles
- WHEN the user logs in successfully
- THEN the access token contains zero permission-code claims
- AND endpoints without `[RequirePermission]` still succeed

### Scenario: Login after permission grant

- GIVEN a user previously without permission `Agents.View`
- AND `PermissionService.AssignToUserAsync(userId, agentsViewId)` was just executed
- WHEN the user logs in (fresh session)
- THEN the access token contains the `Agents.View` claim

## REQ-CLAIMS-02 — Permission code claims at refresh

### Scenario: Refresh reflects current permissions

- GIVEN a user logged in with permission set P1
- AND `PermissionService.AssignToUserAsync` grants P2 before refresh
- WHEN `AuthService.RefreshAsync` rotates the refresh token
- THEN the new access token contains P1 AND P2
- AND the new access token was NOT generated by copying claims from the previous token

### Scenario: Refresh after permission revoke

- GIVEN a user logged in with permission set including `Roles.Delete`
- AND `PermissionService.RemoveFromUserAsync` removes `Roles.Delete`
- WHEN the user refreshes
- THEN the new access token does NOT contain `Roles.Delete`
- AND the previous access token still contains `Roles.Delete` until natural expiry

---

## REQ-CLAIMS-03 — Claim-based PermissionHandler

### Scenario: Authorized endpoint accepts claim

- GIVEN a JWT containing claim `Users.View`
- WHEN a request reaches an endpoint with `[RequirePermission("Users.View")]`
- THEN `PermissionHandler` succeeds
- AND `IPermissionService.UserHasPermissionAsync` is NOT invoked (assert via test spy)

### Scenario: Unauthorized endpoint rejects missing claim

- GIVEN a JWT that does NOT contain `Users.Delete`
- WHEN a request reaches an endpoint with `[RequirePermission("Users.Delete")]`
- THEN the response is 403 Forbidden
- AND `IPermissionService.UserHasPermissionAsync` is NOT invoked

### Scenario: Backward compatibility for non-permission endpoints

- GIVEN a JWT without permission claims (e.g. `app` user with no permissions)
- WHEN a request reaches an endpoint WITHOUT `[RequirePermission]`
- THEN authorization succeeds

## REQ-STAMP-02 — Audience-conditional stamp check

### Scenario: ERP token triggers stamp check

- GIVEN a valid JWT with `aud == "erp"`
- WHEN the token is presented on any request
- THEN `ISecurityStampValidator.ValidateAsync` is invoked exactly once
- AND `UserManager<ApplicationUser>.FindByIdAsync` is called once

### Scenario: APP token skips stamp check

- GIVEN a valid JWT with `aud == "app"`
- WHEN the token is presented on any request
- THEN `ISecurityStampValidator.ValidateAsync` is NOT invoked
- AND `UserManager<ApplicationUser>.FindByIdAsync` is NOT called on the auth path

### Scenario: Token with unknown audience is rejected before stamp check

- GIVEN a JWT with `aud == "some-other-app"` (not in `ValidAudiences`)
- WHEN the token is presented
- THEN the response is 401 Unauthorized (audience validation, not stamp validation)
- AND `ISecurityStampValidator.ValidateAsync` is NOT invoked

## REQ-STAMP-03 — Stamp check outcome

### Scenario: Stamp mismatch denies ERP request

- GIVEN a user with a JWT whose `security_stamp` claim matches the user's stored stamp
- AND `TokenInvalidationService.InvalidateUserTokensAsync(userId)` is called (bumps stamp)
- WHEN the prior JWT is presented on a new request with `aud == "erp"`
- THEN the response is 401 Unauthorized

### Scenario: Disabled ERP user denied via stamp

- GIVEN an active ERP user with a valid JWT
- AND `UserService.UpdateAsync` flips `IsActive` to `false` AND bumps the stamp
- WHEN the JWT is presented
- THEN the response is 401 Unauthorized

### Scenario: Deleted user denied via stamp

- GIVEN an ERP user that has been deleted from the DB
- AND a JWT with that user's id and original stamp
- WHEN the JWT is presented with `aud == "erp"`
- THEN `ValidateAsync` returns false (user not found)
- AND the response is 401 Unauthorized

## REQ-INVALID-01 — Stamp bump on permission mutation (already implemented)

### Scenario: Assign permission to user bumps stamp

- GIVEN an active user
- WHEN `PermissionService.AssignToUserAsync(userId, permissionId)` succeeds
- THEN `ITokenInvalidationService.InvalidateUserTokensAsync(userId)` was called once
- AND the user's stored `SecurityStamp` differs from its previous value

### Scenario: Assign permission to role bumps stamp for all affected users

- GIVEN a role R with users U1, U2, U3
- WHEN `PermissionService.AssignToRoleAsync(R, permissionId)` succeeds
- THEN `InvalidateUsersTokensAsync` is called ONCE with {U1, U2, U3}
- AND the stored `SecurityStamp` of U1, U2, U3 all differ from their previous values

### Scenario: Remove permission from role bumps stamp for all affected users

- GIVEN a role R with users U1, U2 and permission P already assigned to R
- WHEN `PermissionService.RemoveFromRoleAsync(R, P)` succeeds
- THEN `InvalidateUsersTokensAsync` is called ONCE with {U1, U2}
- AND the per-user `InvalidateUserTokensAsync` is NOT called (no loop)

---

## REQ-INVALID-05 — Batched invalidation (single UPDATE)

### Scenario: Batch invalidates all affected users in one statement

- GIVEN 3 users with known security stamps
- WHEN `InvalidateUsersTokensAsync({U1, U2, U3})` is called
- THEN all 3 stored stamps change
- AND the operation executes as a single `ExecuteUpdateAsync ... WHERE Id IN (...)`

### Scenario: Empty batch is a no-op

- GIVEN no affected users (role without members)
- WHEN `InvalidateUsersTokensAsync([])` is called
- THEN no stamps change and no exception is thrown

### Scenario: Unknown ids are skipped without throwing

- GIVEN 2 existing users plus one non-existent id (deleted user)
- WHEN `InvalidateUsersTokensAsync` is called with all 3 ids
- THEN no exception is thrown
- AND the 2 existing users still get their stamps updated

### Scenario: Cancellation propagates to every invalidation path

- GIVEN a canceled `CancellationToken`
- WHEN either `InvalidateUserTokensAsync` or `InvalidateUsersTokensAsync` is invoked with it
- THEN an `OperationCanceledException` is thrown before/at the DB operation

## REQ-INVALID-03 — Stamp bump on user disable (NEW: gap today)

### Scenario: Disabling user invalidates all tokens

- GIVEN an active user with valid JWT
- WHEN `UserService.UpdateAsync(userId, { IsActive: false })` succeeds
- THEN `ITokenInvalidationService.InvalidateUserTokensAsync(userId)` was called
- AND any subsequent ERP request with the prior JWT returns 401

### Scenario: Re-enable does not clear the stamp bump

- GIVEN a user whose stamp was just bumped by a disable
- WHEN `UserService.UpdateAsync(userId, { IsActive: true })` is called
- THEN the security stamp remains at the bumped value
- AND previously issued JWTs remain invalidated

### Scenario: Non-IsActive update does not bump

- GIVEN an active user
- WHEN `UserService.UpdateAsync` is called with only `FirstName` change
- THEN the security stamp is NOT modified
- AND existing JWTs remain valid

## REQ-AUDIT-01 — Audience isolation on ERP admin endpoints

### Scenario: APP token accepted by middleware but denied on ERP admin endpoints

- GIVEN the real production config (`Jwt:ValidAudiences = ["erp", "app"]`)
- AND a valid JWT with `aud == "app"` carrying ERP permission claims (staff user with access to both apps)
- WHEN the JWT is presented on `[RequireErpAudience]` endpoints (Users/Roles/Permissions)
- THEN the JWT middleware accepts it (both audiences valid)
- AND the `ErpAudience` policy denies it (403 Forbidden)

### Scenario: ERP token accepted on ERP admin endpoints

- GIVEN a valid JWT with `aud == "erp"`
- WHEN the JWT is presented on a `[RequireErpAudience]` endpoint
- THEN the `ErpAudience` policy succeeds
- AND `[RequirePermission]` authorization proceeds as usual

### Scenario: Token without audience claim denied

- GIVEN a valid JWT with no `aud` claim
- WHEN the JWT is presented on a `[RequireErpAudience]` endpoint
- THEN the `ErpAudience` policy denies it

## REQ-AUDIT-03 — ERP-only admin endpoints (attribute coverage)

### Scenario: Admin controllers carry the ERP audience requirement

- GIVEN `UsersController`, `RolesController` and `PermissionsController`
- WHEN inspecting their class-level attributes
- THEN each carries `[RequireErpAudience]`
- AND `AuthController` / `MeController` do NOT (app users must refresh/logout/me)

### Scenario: Anonymous registration stays open

- GIVEN `UsersController` with class-level `[RequireErpAudience]`
- WHEN `POST /api/users` is invoked
- THEN `[AllowAnonymous]` on the action bypasses authorization (registration remains open)

## REQ-REFRESH-01 — Atomic refresh rotation

### Scenario: Concurrent refresh with the same token yields one family

- GIVEN an active refresh token T for user U
- AND two requests present T simultaneously (legitimate client + stolen-token replay)
- WHEN both call `AuthService.RefreshAsync(T)`
- THEN exactly one request succeeds and mints a new token
- AND the other is rejected (returns null) without minting anything
- AND `RevokedAt` is set exactly once for T

### Scenario: Replay after a successful rotation is rejected

- GIVEN token T was just rotated successfully
- WHEN a request presents T again
- THEN `RefreshAsync(T)` returns null
- AND no additional refresh token is minted

---

## REQ-AUDIT-02 — Disabled-user enforcement window

### Scenario: Disabled APP user denied at next refresh

- GIVEN an active patient with valid `app` access token and refresh token
- WHEN `UserService.UpdateAsync` flips `IsActive` to false
- THEN the current access token remains valid until natural expiry (≤ 15 min)
- AND the next `/api/auth/refresh` attempt returns null (refresh revoked at DB level via stamp-driven path)
- AND any subsequent login attempt returns null

### Scenario: Disabled ERP user denied immediately

- GIVEN an active ERP user with valid JWT
- WHEN `IsActive` flips to false AND stamp is bumped
- THEN the next request with the prior JWT returns 401 (stamp mismatch)

## REQ-MIGRATE-01 — Rollout ordering (hard constraint)

### Scenario: Stage 1 alone is safe

- GIVEN `ISecurityStampValidator` wired in DI + `OnTokenValidated` for `aud == erp`
- AND no claim changes yet (stage 2 not started)
- WHEN the deployment ships
- THEN ERP tokens with mismatched stamps are rejected (immediate revocation active)
- AND `app` tokens are unaffected (no stamp check)
- AND `PermissionHandler` still queries DB (no behavior change)

### Scenario: Stage 2 alone is safe (double validation)

- GIVEN permission claims emitted in tokens (REQ-CLAIMS-01/02 active)
- AND `PermissionHandler` still on DB path (REQ-CLAIMS-03 not yet active)
- WHEN a request hits a `[RequirePermission]` endpoint
- THEN the handler authorizes via DB (existing behavior preserved)
- AND claims are present in the JWT but not yet consulted

### Scenario: Stage 3 completes the migration

- GIVEN stages 1 and 2 active in production
- WHEN stage 3 ships (claim-only handler)
- THEN no DB query against `IPermissionService.UserHasPermissionAsync` occurs on the authorization path
- AND ERP revocation remains within one request (stamp check)
- AND APP revocation remains ≤ 15 min (no stamp check)

### Scenario: Reordering stage 3 before stage 1 is a security regression

- GIVEN stage 3 ships BEFORE stage 1 (no stamp validation yet)
- WHEN an ERP user's permissions are revoked
- THEN the user retains access until token expiry (≤ 15 min)
- AND the security regression is documented in the rollout plan
- AND the apply-phase tasks MUST be ordered to make this impossible

## REQ-NGOAL-01 — Non-goals

### Scenario: No refresh-on-deny middleware

- GIVEN any request returning 401
- WHEN the client receives the 401
- THEN the server does NOT auto-issue a new token
- AND the client (front) decides whether to call `/api/auth/refresh` once

### Scenario: No Redis dependency added

- GIVEN this change is deployed
- WHEN reading `CoppAddresd.Auth.csproj`
- THEN no new package dependency on Redis, `StackExchange.Redis`, or `IDistributedCache`

### Scenario: Access token lifetime unchanged

- GIVEN the deployment
- WHEN reading the issued JWT
- THEN the token lifetime equals `JwtSettings.AccessTokenExpirationMinutes` (15 min by default)

### Scenario: No front-end changes shipped

- GIVEN this change is deployed
- WHEN comparing `coppaddresd-front` before and after the change
- THEN `http.ts refreshAccessToken` on 401 behavior is unchanged
- AND no front-end PR is part of this change

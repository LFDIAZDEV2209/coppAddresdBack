Each module owns its schema. `auth.applications` + `auth.user_applications` decide
which application (`erp`/`app`) a user can access. JWT `aud` is the login-time
application code; both services validate with `Jwt:ValidAudiences`.

## Auth Service Endpoints (key ones)

- `POST /api/auth/login` — email + password + application + rememberMe
- `POST /api/auth/refresh` — cookie-based refresh rotation
- `POST /api/auth/logout` — revoke all refresh tokens
- `POST /api/auth/change-password`
- `GET /api/me` — current user + roles + permissions
- CRUD under `/api/users`, `/api/roles`, `/api/permissions`
- Permission seeding: 15 total (Users/Roles/Permissions/Agents CRUD)

Refresh cookie: `copp_refresh_token` (HttpOnly, SameSite=Lax, Path=/api/auth).
Admin credentials: `admin@coppaddresd.com` / `Test@1234`.

## Chat/AI Endpoints

- `POST /api/v1/chat` — sync, via MediatR → AI Service
- `POST /api/v1/chat/stream` — SSE (`text/event-stream`)

Polly: 3 retries (exponential backoff) + circuit breaker (5 failures → 30s break).

## Audit System

- Trigger-based (PostgreSQL INSERT/UPDATE/DELETE).
- Actor propagation via GUC (`audit.actor_type`, `audit.user_id`, …) set
  transactionally with `set_config(..., true)` to avoid pooling leaks.
- `HttpAuditActorContext` currently returns `ActorType=System`, `UserId=null`
  (Identity integration pending).

## Conventions & Gotchas

- **`appsettings.json` / `appsettings.*.json` are gitignored** for Api and Auth.
  Create them locally before running. Only Auth has `appsettings.Example.json`.
- **JWT must be identical** between Api and Auth Service (Secret, Issuer, Audience).
- **Auth Service runs migrations + seeders automatically** at startup.
- **Integration tests** require a real PostgreSQL — env var `COP_TEST_DB_CONNECTION`.
- **Solution file is `.slnx`** (XML). Tools expecting `.sln` fail.
- **Comments/docs in Spanish** by repo convention.
